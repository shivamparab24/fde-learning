CONVERSATION STATE, LANGGRAPH STATE, CHECKPOINTERS & HISTORY STRATEGIES

1. CORE MECHANISMS
--------------------------------------------------------------------------------
Managing conversation state across turns in LangGraph relies on two core mechanisms:

- State Reducers (`add_messages`): Keeps track of message history by appending 
  new turns rather than overwriting the entire state list.
- Checkpointers (`MemorySaver` or Database Checkpointers): Persists graph state 
  at every step using a `thread_id` key, allowing you to resume or continue 
  conversations seamlessly.




2. KEY COMPONENTS & ARCHITECTURE
--------------------------------------------------------------------------------
- Annotated[list, add_messages]:
  Prevents state overwrites. When a node returns {"messages": [new_msg]}, LangGraph 
  calls `add_messages` to append `new_msg` to the existing message array.

- MemorySaver:
  An in-memory key-value checkpointer ideal for testing or short-lived server sessions.

- thread_id:
  The database key used by the checkpointer to read and write state. Different 
  `thread_id`s represent isolated conversation threads.

- Execution Flow:
  [ User Input ] ---> langgraph.stream(..., config) ---> [ Output Stream ]
                                 ^
                                 | Read / Write
                                 v
                     +-----------------------+
                     |      Checkpointer     |
                     |  (MemorySaver / DB)   |
                     +-----------------------+
                     config = {"thread_id": "session_id"}





3. CODE IMPLEMENTATION (LangChain Ollama + MemorySaver CLI)
--------------------------------------------------------------------------------
from typing import Annotated
from typing_extensions import TypedDict
from langchain_ollama import ChatOllama
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    messages: Annotated[list, add_messages]

llm = ChatOllama(model="llama3", temperature=0.7)

def chatbot_node(state: State):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

builder = StateGraph(State)
builder.add_node("chatbot", chatbot_node)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

checkpointer = MemorySaver()
graph = builder.compile(checkpointer=checkpointer)


4. WINDOWED VS. RUNNING-SUMMARY HISTORY TRADE-OFFS
--------------------------------------------------------------------------------

A. Windowed History (Sliding Window)
   - Concept: Keeps only the N most recent messages (or within token limit) and 
     discards older ones.
   - Pros: Low latency/cost, exact recall for recent context, zero extra API calls.
   - Cons: Catastrophic forgetting of early conversation facts, potential task breaks.

B. Running-Summary History
   - Concept: Periodically uses an LLM to condense older turns into a concise narrative 
     summary attached to recent raw messages.
   - Pros: Infinite long-term memory retention, smooth context degradation.
   - Cons: Extra LLM API calls/latency, potential loss or distortion of fine details.

C. Comparison Matrix:
   +---------------------------+------------------+-------------------------+
   | Feature                   | Windowed History | Running-Summary History |
   +---------------------------+------------------+-------------------------+
   | Context Retention         | Drops old state  | Preserves key concepts  |
   | Token Cost                | Predictable/Low  | Low input + Summary gen |
   | Latency                   | Fast             | Slower when summarizing |
   | Implementation Complexity | Simple           | Moderate                |
   | Ideal Use Case            | Short tasks      | Long-form assistants    |
   +---------------------------+------------------+-------------------------+
